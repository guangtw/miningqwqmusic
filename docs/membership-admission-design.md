# 会员申请调度与运维设计（membership-v1）

> 熟人优先扩展已实现但默认关闭。本文FIFO与全队列预算描述适用于`admissionMode=legacy`；`familiar-first`改用分队候选和独立预算，普通仅使用保护空位以外的正常区。容量公式、15硬顶、软区条件、邮件和兑换协议不变。接口、切换及回滚见[后端契约](familiar-backend-contract.md)。

## 已确认边界

无下限；正常发放后人数及预留合计严格少于10；15为包含永久会员的硬顶。正常时长为3/7天，软限制区只发3天。队首等待满24h、距上次软区发码满24h，且未来24h不会出现正常名额时，每24h最多放行1人。账号密码登录保留，邮箱辅助登录仅用于已有账号。申请前确认邮箱，验证码登录成功即确认邮箱。

## 容量不变量

C = 有效 PlaybackAuthorization 账号数 + 尚未转换授权的历史 MusicUnblockEntitlement 数 + 有效未兑换邀请码数。
有效授权必须 status=active、revokedAt=null、expiresAt为空或大于服务端now。邀请码必须 status=active、redeemedByUserId为空、兑换截止为空或大于now。没有截止时间的历史码永久占预留，不能假设不会兑换。

发行新码/人工新增会员：同一写事务检查 C+新增数量<=15。申请发码先预留再发送；兑换将预留转换成授权。原会员使用新人工码续期不增加人数。历史承诺若已超过15，自动开放检查拒绝，保留原权益，不擅自作废旧码；新用户兑换另检查实际有效会员不能超过15。

所有写入口使用 SQLite writer lock；进程内加有界FIFO（最多256个待执行事务）避免突发请求耗尽SQLite连接池，进程间仍以数据库锁为准。读完人数再在另一个事务写入是不允许的。

## 时长公式

正常容量预算以9为上边界（发放后严格少于10）。H=8天：
B(t) = integral[t,t+8d] max(0,9-C_hat(u))du，单位人天；
b=B/max(1,Q)，Q为当前待处理队列大小；
b>=6发7天，否则发3天。阈值6为“24h兑换预留+3天”和“24h兑换预留+7天”最坏占用4/8人天的中点。
在全部已知到期事件上分段积分，无小时取整误差。待兑换限时码按最晚兑换时刻+会员时长计占用；永久码无限占用。一次批次冻结正常时长，减少同批待遇因逐个发放计算变化。

这个预算是时长调度器，不预订未来新增名额，也不承诺预测未来申请。硬顶由实时事务保障；软区用24h等待、24h间隔和已知释放事件三项控制。队列按queuedAt、id排序。无人申请时只维护状态，不发码。

## 后台与私密数据

PM2进程 miningqwq-membership-worker 从当前账户发布目录运行 scripts/membership-worker.mjs，复用原.env/数据库，不需要Redis或新增公网端口。每轮调度、清理失效任务、更新心跳并发送队列邮件；provider I/O在数据库事务之外。发送前检查任务对应挑战/申请/用户邮箱仍有效。

邮件任务领取120秒租约，租约过期可被另一Worker恢复；SMTP发送后以租约token条件确认。自动最多5次尝试，15/30/60/120秒退避（上限300秒）。网络结果不明可能重复收到同一张码，但不生成新码、不重复授权。失败耗尽仍保留固定截止时间内的预留，防止可能已送达的旧码成为幽灵名额；用户可重发、管理员可重试或取消。

OTP仅存HMAC摘要；Outbox正文用AES-256-GCM加密，HKDF从稳定AUTH_JWT_SECRET分别派生验证/邮件密钥，不能在发布中更换JWT秘密。原始申请码仅在加密队列和投递邮件中存在。成功兑换/验证或过期/取消后清除载荷；过期任务和挑战再保留7天安全元数据，审计180天。没有公开查码API。

验证码用途独立；6位、10分钟、最多5次错误，一次使用。持久限速跨进程/重启有效：同邮箱发送间隔60秒、10次/24h，IP50次/24h，OTP请求全站300次/24h；验证IP30次/15min；实际邮件发送全站300次/24h。限额键中邮箱和IP使用HMAC，不保存原始IP。

已有SMTP配置继续使用共享私有文件，所有动态文案沿用品牌HTML+纯文本+内嵌Logo。邮件投递不能保证收件箱到达或精确一次；系统保证同一兑换码/授权幂等。

## 迁移、发布与回滚

新增两个可空字段及六张表，不改密码、JWT秘密、原授权、原邀请码、会话或上传目录。迁移20261104120000_membership_applications保留前/后schema和SQL三项SHA256计划；事务内对所有原表的原字段逐行摘要，前后完全一致、外键检查通过后提交；支持重复执行并拒绝部分结构。

发布沿用 npm run deploy:echo -- --push。先备份含WAL的原数据库，精确校验迁移链，再构建/候选/正式验收。正式服务启动Worker并核验数据库心跳；回滚恢复原Worker（原先没有则移除新Worker）。不恢复旧数据库覆盖新写入数据。

首次发布后 MembershipPolicy 默认 applicationsOpen=false、dispatchEnabled=false、emailLoginEnabled=true。前端联调前不会自动批准或向申请者发码。部署回归只做不发送真实邮件的权限、契约和无效验证码检查；实际用户请求按上述业务发信，无部署自动自发自收测试。

前端交付后管理员PATCH开关：
{"applicationsOpen":true,"dispatchEnabled":true}
暂停新申请与发码：
{"applicationsOpen":false,"dispatchEnabled":false}
已预留的码仍可兑换，已获批邮件仍按原任务投递。若需取消具体预留，使用管理员cancel/block而不是直接删除数据库行。

启用前读取管理员状态清点历史有效码；不可因实际活跃账号少就忽略它们。今后若回滚到不支持本体系的旧源码，必须先停新申请/发码并控制全部会员写入口，避免旧发行脚本绕过硬顶。既有新增表和用户数据保留；不做破坏式降级。
