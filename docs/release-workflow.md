# 可重复的生产发布

在 `C:\MiningQwQMusic` 执行：

```powershell
npm run deploy:echo -- --push
```

先提交本次准备发布的源码。脚本发布两个仓库的 **HEAD 提交**，不打包工作目录里的未提交文件。账户仓库默认在相邻目录 `C:\MiningQwQLogin`，可用 `ECHO_LOGIN_REPO` 指定。账户服务源码也会随完整发布包上传到 `miningqwqmusic` 的 GitHub Release，版本清单同时记录两个仓库的提交。

脚本按顺序执行：

1. 首先验证 SSH 与 `sudo -n`，连接问题在构建前暴露；拉取 GitHub 引用，如果本地落后或分叉就停止，不覆盖新前端。
2. 从 Git 导出两个确定的提交到临时目录，排除 `.env`、SQLite 数据、头像上传和密钥。默认在隔离目录 `npm ci`，运行两个仓库的单元/集成测试，再构建音乐站生产版本，单 Worker 运行桌面、手机浏览器测试，避免开发服务器的动态编译/HMR 和本机资源竞争影响时序。浏览器使用独占的 3047 端口，不能误用另一个开发服务器；普通本地 `test:e2e` 仍默认开发模式和两个 Worker。
3. 生成完整源代码包、逐文件 SHA-256 清单以及传输包 SHA-256，通过 SCP 上传。
4. 服务端取得发布锁，后台独立执行。SSH 中断不会停止已经启动的发布/回滚任务。复用线上配置、数据库和头像；依赖锁文件一致才复用 Linux 依赖，否则重新安装。两个服务按顺序构建，限制构建内存。
5. 使用仅监听回环地址的 3101/3102 候选服务，验证真实注册、登录、Cookie 续期、只读播放权限检查、旧 Cookie 不覆盖新 Cookie、收藏增删及退出。另用两个隔离账号验证一起听的实时 SSE、进度/暂停、防过期报告、房主转交和队列清空。测试账号按随机邮箱和 ID 精确清理。
6. 保存旧配置，仅切换账户与音乐服务。正式 HTTPS 上重复验证；任何切换后失败都会尝试恢复原音乐链接和原账户进程配置。保留发布日志及旧版本。数据库结构仅允许下述精确校验的增量迁移，应用回滚保留其兼容新增表和用户新数据。
7. 检查公开的 `/__deployment.json` 是否与本次两个提交完全一致。只有出现 `PRODUCTION_VERIFIED` 才表示上线通过；随后推送确切提交（不强推），校验 GitHub 分支，并上传包含前后端源码的完整 GitHub Release 包。

`--prepare-only` 仅导出和校验发布包，不测试、不上传、不部署、不推送。`--reuse-local-deps` 用于已验证的本机依赖：仅当当前锁文件与提交中的锁文件一致时，链接现有依赖到隔离测试目录；默认仍为 `npm ci`。视觉对比需要独立的上游参考服务，本脚本不把缺失的参考对比当作已通过。

音乐上游保护与参数见 [请求保护说明](music-upstream-protection.md)。发布时只迁移已知失效的旧音源预设 `kuwo,kugou,migu`；候选验证后才更新共享配置，配置备份仅保存在服务器受保护的发布目录，失败时恢复。

客户端安装包独立于网站发布包，公开下载与 Claude 前端接口见 [下载交接](client-downloads-frontend-handoff.md)。清单升版前先运行 `node ops/scripts/sync-client-downloads.mjs` 上传并核对 EXE/APK，再走标准网站发布。候选与正式验收都会核对目录接口和文件 HEAD/Range；网站回滚不会删除持久目录中的安装包。网站不提供便携 ZIP。

联合修复发布还会确认 `netease-api-v2` 出口标识后取消 BFF 重复限速，保存并恢复原音乐进程配置；网易额度为突发 3、每秒补充 1、在途 2。登录来源信任只在 Nginx 覆盖真实地址、音乐和账户进程均仅监听回环时开启。候选用隔离测试账号验证同邮箱不同来源互不锁定，正式 HTTPS 验证伪造转发头不能绕过锁定，并核验 Retry-After。测试账号按 ID 和随机邮箱精确删除。见 [联合修复规划](backend-request-and-login-repair-plan.md)。

## 网络检查

服务器保持现有密钥认证、严格主机密钥校验、单 IP 白名单和已授权的 sudo。校园网公网出口会变化，持久化 sudo 不会使旧 IP 白名单自动匹配新出口。

Windows 的 VPN 劫持路由时，可执行一次：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ops/scripts/repair-echo-route.ps1
ssh aliyun-ai 'sudo -n true && echo READY'
```

路由脚本仅为服务器 `47.122.113.9/32` 设置 WLAN 网关的持久化直连。切换到不同网络网关时先核对并更新这条路由；不要关闭整个 VPN 或放开 SSH 全网访问。路由正确但连接仍超时，需要核对当前公网出口与云防火墙单 IP 规则。

## 失败后检查

本机临时目录内的 `receipt.json` 记录发布 ID、源码提交与包校验值。服务器任务位于 `/home/aiops/releases/<发布ID>/`，其中 `job.log` 为发布输出，`result.json` 为最终状态。不要在发布结果未知时重复启动第二次发布。

受保护的构建日志、原运行配置与完成标记位于 `/www/wwwroot/miningqwqmusic/shared/deploy-backups/<发布ID>/`，只通过 sudo 读取，不上传到 GitHub。数据库 schema 变化默认停止发布；只允许一人一码会员、原私信、音乐卡片元数据迁移组成的已知链，每步旧 schema、新 schema、迁移 SQL 三个 SHA-256 必须完全匹配专用计划。历史迁移保留目标schema快照以校验逐步执行，不拿最终schema替代中间目标。迁移前对原库做包含WAL的在线备份；私信迁移检查原有数据摘要、外键及新增表完整性。应用回滚保留新增表及新消息，不自动用旧备份覆盖现有数据库。详见 [会员协议](membership-invitations.md)、[基础后端交接](backend-social-playlist-handoff.md) 和 [卡片/邀请交接](backend-rich-messages-handoff.md)。

候选及正式验收还会运行 `verify-social-playlist-session.cjs`：以两个临时 `@example.test` 账号验证陌生人限额、幂等、回复解锁、好友关系、SSE及日志补拉、已读、歌单原子排序和首曲封面、音乐卡片/自建歌单快照、自动邀请消息及接受状态，再检查真实只读评论及写入405。测试用户按精确ID与邮箱删除，消息和事件级联清理；这不是本机开发阶段的自动上线入口。

GitHub 推送或 Release 上传失败不会撤销已经通过验收的生产版本。此时根据明确的 `PRODUCTION_VERIFIED` 记录补推相同提交或发布包，不重复部署。
